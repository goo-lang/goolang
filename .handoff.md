### The defect itself

`parts = append(parts, x)` is NOT a rebind. goo_slice_append reallocs, and
goo_realloc frees the old base ITSELF, so the pointer still in the slot is
already dangling when the store runs and the release-before-store read it.

Fixed by calling `release_decision_is_self_append` — the SAME predicate the
rebind rule uses, exported rather than reimplemented, because the two must agree
or one of them frees live memory. `selfAppend` joined the probe fixture, and the
guard IS mutation-tested: disabling the check makes the probe FAIL on differing
output. That test is the only reason this shape is now guarded rather than
merely fixed.

**THREE MEMORY DEFECTS IN THIS ARC LEG, AND THEY ARE NOT ONE PATTERN.** Keeping
them apart matters, because the fix differs:

- **#275** — a refcount panic and a segfault. Found by a security review.
- **#278** — the switch/type-switch depth mismatch: `cfctx.loop_depth` and
  release_decision's `block_depth` are two counters maintained by DIFFERENT code
  and assumed equal. verify-core, 493 goldens, a new valgrind probe and an 8/8
  teeth run were all GENUINELY green over it. No corpus can see that invariant,
  which is why it took a diff review.
- **#284** — the self-append. Here the corpus WAS able to see it and simply had
  not been asked (measured: 2 goldens fail). Not the same class as #278 at all.

So the honest tally is ONE defect that gates could not have caught (#278) and
one that a gate already in the tree would have caught (#284). "Our gates are
blind" is the wrong conclusion, and it is the expensive one -- it argues for
building new machinery when the first move is to RUN what exists, in order:
`make test-golden`, then the daemon, then read the diff.

## The second defect, which cost the whole win rather than safety

`has_alias` first counted EVERY mention, so `u := strings.ToUpper(last)` — an
ordinary read into a new local, which COPIES — read as an alias. The daemon

**A FIFTH, found in #264: valgrind is BLIND to half of the substring hazard.**
Measured by making `binding_is_owned` accept `AST_SLICE_INDEX_EXPR`:

- `low=1` -- `interior - 16` lands in the REAL header, reads refcount 0, and
  `goo_release` panics. Exit 2, and the rc check catches it.
- `low=32` -- it lands in the PAYLOAD, reads a large non-zero count, so the
  underflow panic never fires and the count never reaches 0. The atomic
  `fetch_sub` then WRITES a decrement into the middle of the string and returns.
  No `free()`, NO VALGRIND ERROR, exit 0 -- SILENT CORRUPTION of eight bytes.

So the runtime's refcount-0 panic is an ACCIDENTAL defence whose reach depends on
the offset, and it must never be relied on. `examples/arc_release_substring_probe

`GOO_ARC_RELEASE=0` control. A valgrind-only check had no teeth against half of
its own subject.

**A LIVE BUG, and the plan that found it was looking somewhere else (#265).**
While planning the switch cliff, reading `codegen_alloc_local_promoted` showed
that an ordinary local gets an ENTRY-BLOCK alloca while its initialising store
stays at the declaration site. So a local declared in a conditional block has a
slot on every path and a VALUE only on the taken one, and an LLVM alloca is undef.
Measured on `if c { a := new(int) }` with c false:

    Use of uninitialised value of size 8
       at goo_release (runtime.c:203)      <- the immortal-count read
     Uninitialised value was created by a stack allocation at f

and again at runtime.c:215, the `__atomic_fetch_sub` -- a WRITE through the
garbage pointer to an arbitrary address. **The program still exited 0.** Only
valgrind saw it. Reachable through a plain `if` since #261, unnoticed for four
increments, and found by reading code rather than by any test.

**AND THE PROBE FOR IT WAS VACUOUS ON THE FIRST DRAFT.** `sink = sink + *alive`
tripped the `AST_UNARY_EXPR` arm, marked `alive` escaping, and released NOTHING --
the probe passed while measuring nothing. Caught by checking the `[arc]` debug
line, not by review. `examples/arc_release_probe.goo` already records that arm as
the reason it increments a counter; the lesson did not transfer until it was
measured again.

**#267, AND THE COMMENT WAS WRONG BEFORE THE MEASUREMENT WAS.** The entry-block
zero store had to go immediately after the alloca, NOT before the entry block's
terminator the way `defer_entry_store_zero` does — when it runs, the entry block
has no terminator yet, so "before the terminator" degrades to "at the end", after
a function-scope local's own initialising store. The first draft of the comment
asserted this would "silently become a no-op and leak". Building that variant
showed the real symptom: an immediate nil-deref panic, exit 2, with a 24-byte
leak that is the panic and not a near miss. The claim was right and the mechanism
in the comment was not, and only the build separated them.

**#274, AND THE GATE ITSELF HAD THE HOLE.** With the element-ownership rule
mutated to claim ownership UNCONDITIONALLY, `make arc-release-probe` still
PASSED. Nothing in the suite appended a value the CALLER owns, which is the only
shape where a wrong answer corrupts memory instead of over-reclaiming. The unit
rows caught it; the end-to-end gate did not.

AND THE PROBE WRITTEN TO CLOSE THAT WAS ITSELF VACUOUS. Its first draft checked
`len(owned)` after the call, which loads field 1 of the `{i8*, i64}` string and
never dereferences the buffer — so it passed against the exact mutant it existed
to catch. Reading the BYTES through a concat makes it report `Invalid read of
size 2` against the mutant and stay clean against the real compiler. Two layers
of instrument failure in one change, both found by asking "can this go red?"
rather than "is it green?".

**#268, AND AN OVER-CONSERVATIVE DEFAULT HIDES HOW LITTLE THE SUITES TEST.**
Fixing the select comm arm made SEVEN matrix cells move from GAP to COVERED
without a single row being written for them. The cause: while `escape_mark_all`
marked every site regardless, a mutation to an expression arm could not change
any verdict, so those cells read GAP. `escape_mark_all` was masking arm coverage
as well as costing precision. Any future `default:` that marks everything should
be read the same way — it makes the matrix under-report.

**#269, AND THE SAME PARTIAL READ TWICE IN ONE AFTERNOON.** valgrind reports
`definitely lost` and `indirectly lost` separately, and a container that holds
leaked children lands in a `(X direct, Y indirect)` record that a naive grep does
not match. The element-scan spike hit this first: its table omitted the two
LARGEST records, including the map at 40.8%. Three hours later the map probe hit
it again — OFF and ON both read 400,000 `definitely lost`, which looks like "the
release does nothing", when OFF was 1,200,000 total and ON was 800,000. **When
reading a valgrind leak, read definite AND indirect, and check the parsed total
against the summary line.** Both times the tell was a number that looked too
tidy.

## The design, for whoever picks this up

**Four conditions, all of which must hold** (`include/release_decision.h`):

1. `local_escape` says the value does not outlive the function.
2. The local OWNS the value, decided at the BINDING SITE.
3. Not declared inside `arena { }` (an arena pointer has no header).
4. Bound ONCE at function scope — not in a loop, and not re-assigned.

**The soundness direction is INVERTED from the escape passes.** There
`escapes = true` is safe. Here `release = false` is safe, so every unrecognised
path refuses and records WHY. `ReleaseVerdict` carries the cause, and every row
asserts the cause rather than a bare boolean.

**Condition 2 is a binding-site table, NOT ADR 0004's origin-emptiness.** That
proposal is constant-false: `local_escape`'s slots ARE local indices and a local
keeps its own bit for life, so no local's taint is ever empty. Measured in #259.
The working rule: `new(T)`/`&T{}` and composite literals are owned, a Goo call is
owned iff its callee's `return_escapes` is false, a shim call iff `non_retaining`
is 1, and a slice/index/selector or bare identifier is NOT owned.

**`ArcReleaseSite.field` says WHICH part of a slot is the object.** `-1` is the
slot's contents (a bare pointer, and a map, whose LLVM form is already `i8*`).
`0` is a fat value's buffer, and only `TYPE_SLICE` uses it.
**`TYPE_INTERFACE` is `{ vtable*, data* }` — field 0 there is the VTABLE, so there
is no general "release field 0" rule and never can be.**

**Ordering is STRUCTURAL.** `codegen_emit_deferred_calls` is a wrapper that runs
defers then releases, because a Go defer runs before the return and can read a
local through a closure. The 8 exit paths cannot drift.

**The release list is captured at DECLARATION time**, in `vscope_add`. Reading the
value table at exit emitted NOTHING — the function body is a block statement, so
`vscope_exit` truncates its locals first.

**`GOO_ARC_RELEASE=0` is the kill switch.** It leaves the plan NULL and emits
nothing. Every probe and `arena_rss_probe.sh` uses it as the control.

## The direction, stated plainly

Last session's close-out said "nothing this session freed a single byte". This one
freed 115.8 MB on the benchmark that motivated ADR 0002, and the way it got there
was refusing to trust a projection. Five plans were invalidated by a measurement
that cost seconds, and four instruments were caught lying before their output was
believed.

`TYPE_STRING` shipped in #264, then #265 and #266 closed the switch cliff — and
between them they produced this session's sharpest lesson. The plan for #266 was
"add recursion plus rows". Reading the codegen first found a LIVE use-of-undef bug
that had been reachable through a plain `if` since #261, and that bug had to ship
FIRST because the four arms would have multiplied its reach. A plan that had gone
straight to the feature would have widened a memory-corruption path.

#267 then finished the job #266 started: the zero store converted condition 5's
refusal into reclamation, so a local declared inside an `if` or a `switch` case
body now reclaims like any other. Three increments, one live bug closed, and the
daemon moved by nothing at all — every one of them was worth shipping anyway,
because the bug was real and the precision is real, and the daemon simply does
not have the shapes they unlock.

checking its debug line, a row that passed on the wrong condition, a comment

#268 fixed the select over-marking, and #269 gave the release path a destructor
