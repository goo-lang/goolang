   Lines, columns and folded-value messages are all fixed; diagnostics now
   match Go's line:column on the pinned cases. Only two low-value residuals

   node is already correct, and integer-literal spelling fidelity in
   rendered expressions.
   Root cause found and it was ONE shared cause, not two: the parser had no
   location tracking at all. `get_current_position()` (parser_actions.c)
   returns `current_lexer->pos`, the LIVE lexer cursor, which by the time a
   bison reduction ACTION runs holds the position of the LOOKAHEAD token
   bison has already read. Proof it was a token position and not a `line+1`
   offset: an error on a line followed by a BLANK line reported the line
   after the blank one — it skipped to the next line bearing a token.
   `identifier:` was the highest-leverage single site, because func_decl /
   package_decl / import_spec / labels all stamp themselves from
   `ident->base.pos` rather than fetching their own — which looked like a
   correct second strategy but was only propagating the identifier's own
   offset position.

     one too large, because `lexer_read_char` advanced `pos` based on the
     character it was LOADING and `lexer_new` primed `column = 1` before the
     first load. The first attempt (init `column = 0` + newline resets to 0)
     was reverted in the batch-1 arc for producing **column 0** on the ASI
     path; the diagnosis that made the real fix obvious is that advancing on
     the loaded character ALSO moves line/column onto the next line the
     moment `ch` becomes `'\n'`, so an ASI position captured there describes

     first character at 1:1. Ride-along improvement: the ASI-inserted
     semicolon now carries the newline's own position (end of the statement

  logic into shared `codegen_emit_variadic_pack` — the same two-loops-drift
  cause that motivated `codegen_coerce_arg_to_param`. Pinned by

  go1.26.1). `a.m(s...)` had worked by ACCIDENT (with spread there is exactly
  one trailing actual, so positional mapping lands the slice correctly) and
  is now a regression pin.
- RESOLVED (interface-variadic arc, PR #225): **variadic methods in an
  INTERFACE**. Ledgered as three stacked defects; it was ONE root cause plus one
  independent consequence.
  *Root* (`d38d015`): the interface-type builder (the `AST_FUNC_DECL` arm of
  `type_from_ast`'s `AST_INTERFACE_TYPE` case) was the FOURTH place in the
  checker that walks an AST param chain to build a function `Type*`, and the
  only one that never applied the `...T` → `[]T` wrap nor set `is_variadic` —
  unlike `declare_function_signature`, the `AST_FUNC_TYPE` arm below it, and
  `type_check_func_lit`. So the interface wanted `T` while every correct impl
  carried `[]T`. The recorded discriminator (an interface declaring `ns []int`
  IS satisfied by an impl declaring `ns ...int`, but `ns ...int` in the
  interface fails against BOTH spellings) pointed straight at it.
  *Ledgered defect 2 was a SYMPTOM, not a peer*: interface-method call arity,
  the spread pre-checks and the per-arg element-type rules all read
  `is_variadic` off the same `im->type` pointer, and the interface arm already
  set `check_signature=1, recv_offset=0`, so all of them corrected themselves
  once the builder did. Verified by watching the probe's failure MOVE from 22
  type errors to module verification — that transition, not a green run, is
  what proved subsumption.
  *Genuinely independent* (`dd7ff6f`): the interface DISPATCH loop, and worse
  than ledgered — it was a bare 1:1 positional walk missing ALL FIVE
  per-argument steps, not just the variadic pack. The same run emitted raw
  element ADDRESSES for struct-field args and unboxed concretes for an `...any`
  param. Fixed by extracting `codegen_emit_fixed_call_arg` and routing all
  three loops through it. `codegen_interface_dispatch` and `build_thunk` needed
  NO change — both build from `im->type` and forward 1:1, so they agree
  automatically once `param_types[last]` is `[]T`.
  Ride-along: `type_interface_satisfied` now compares `is_variadic` (Go treats
  variadicity as part of the signature, and the #105 model lowers both
  spellings to the same `[]int` slot, so `type_equals` cannot see the
  difference) — a new REJECTION, no existing fixture relied on the pairing.
  Plus a non-final-variadic guard in the interface builder, mirroring
  `declare_function_signature`'s.
  Pinned by `examples/iface_variadic_probe.goo` (expected output from `go run`,
  go1.26.1) + `tests/golden/reject/iface_variadic_nonfinal_reject.goo` and
  `iface_variadic_mismatch_reject.goo`. All three verified RED first — the
  nonfinal fixture was ACCEPTED at rc=0.
