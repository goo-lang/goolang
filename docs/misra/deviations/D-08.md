> Rule 21.10: The Standard Library time and date functions shall not be used.

## Summary

The compiler measures elapsed time for the performance monitor and for the
`goo test` runner, and the language's own `time` shim package needs a clock to
implement.

Baseline: 47 reports in hand-written code.

## Detailed description

MISRA's rationale is that most of `<time.h>` is implementation-defined:
`time_t`'s representation and epoch are unspecified, `localtime` and `gmtime`
return a pointer to a static object that the next call overwrites, and
`asctime` and `ctime` write into a static buffer whose contents are not
preserved. Rules 21.19 and 21.20 cover the static-buffer half separately, and
this project is clean against both.

The uses here are of the monotonic-clock kind rather than the calendar kind:

```c
uint64_t performance_get_timestamp_ns(void) {
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return (uint64_t)ts.tv_sec * 1000000000ULL + (uint64_t)ts.tv_nsec;
}
```

`clock_gettime(CLOCK_MONOTONIC, ...)` has none of the properties MISRA objects
to. It is POSIX rather than ISO C, it returns a value with a defined
representation, and it uses no static storage.

## Justification

- **Comply by removing timing.** Rejected. The performance monitor and the
  benchmark figures in ADR 0002 and ADR 0005 depend on it, and those
  measurements are load-bearing for the memory-model decisions.
- **Comply by using a platform clock directly.** `clock_gettime` already is
  that; the addon reports it because it is in the `<time.h>` family. There is
  nothing further to move to.
- **Deviate.** Adopted.

## Conditions under which the deviation is requested

Monotonic and process-clock reads: `clock_gettime`, `clock`, and the
`struct timespec` arithmetic around them.

Calendar functions with static storage — `localtime`, `gmtime`, `asctime`,
`ctime` — are **excluded**. Rules 21.19 and 21.20 remain adopted and clean, and
introducing one of these functions would break them as well as this deviation.

## Consequences of non-compliance

`CLOCK_MONOTONIC` is not affected by wall-clock adjustment, so an elapsed-time
measurement cannot go backwards. A timestamp captured on one machine is not
comparable with one from another, which matters only for the benchmark figures,
and the measurement discipline for those is already recorded in the project's
memory-model documentation: quote bytes, or re-measure all builds together.
