> Rule 21.3: The memory allocation and deallocation functions of `<stdlib.h>`
> shall not be used.

## Summary

The compiler allocates on the heap on essentially every code path. The AST, the
type table, the symbol tables, the string interner, the diagnostic buffers and
the emitted IR are all heap-resident and all sized by the input program.
Complying with Rule 21.3 would mean rewriting the compiler around a static
memory budget, which is not possible for a tool whose working set is a function
of the source file it is given.

Baseline: 2,597 reports in hand-written code.

## Detailed description

MISRA's rationale for Rule 21.3 is that `malloc`, `calloc`, `realloc` and `free`
have undefined behaviour in several documented cases, that allocation can fail
at run time, and that a long-running system can fragment its heap until an
allocation that succeeded during test fails in the field. All three concerns are
real. None of them applies in the same way to a batch compiler process that
starts, reads a bounded input, writes an object file and exits.

The project does not call the `<stdlib.h>` functions directly in most places. It
calls the wrappers in `include/xalloc.h`:

```c
static inline void *xmalloc(size_t size);
static inline void *xcalloc(size_t nmemb, size_t size);
static inline void *xrealloc(void *ptr, size_t size);
static inline char *xstrdup(const char *s);
```

`xalloc.h` is force-included into every translation unit by `CFLAGS`. Each
wrapper checks the result, writes a diagnostic to `stderr` and calls `exit(1)`,
so the "allocation may fail silently" half of MISRA's rationale is already
answered at the point of call: there is no code path in which a null result
from an allocator is treated as a valid pointer. That `exit` call is itself
covered by D-09.

Lifetime is managed by automatic reference counting, accepted in
`docs/adr/0002-memory-model-arc-with-escape-analysis-elision.md`, with escape
analysis as the elision pass. On the 400,000-request daemon benchmark, ARC
reclaims 96.7% of peak RSS against the release-off control, and valgrind reports
zero errors.

## Justification

Complying is not achievable. A compiler's peak memory is set by the program it
is compiling, and this one has no upper bound on input size. A static pool sized
for the largest expected input would either be far too small for a real program
or would waste hundreds of megabytes on a small one.

The following alternatives were considered:

- **Static pools sized at build time.** Rejected. Any fixed size is either
  wrong for large inputs or wasteful for small ones, and it converts a
  recoverable out-of-memory abort into a compile failure with no diagnostic.
- **Arena allocation only, with no individual `free`.** Partly adopted already
  through `arena { ... }`, but ADR 0002 measured its reach as narrower than the
  syntax suggests: an arena reclaims only the allocation sites codegen emits
  directly, and every allocation made through a runtime helper is untouched.
  It cannot replace the general allocator.
- **A custom allocator that is not `<stdlib.h>`.** This would satisfy the
  letter of Rule 21.3 while changing nothing about the risk, and it would put
  the project's own allocator between the code and the sanitizers that
  currently find its bugs. Rejected as a rule-lawyering change that makes the
  software worse.

## Conditions under which the deviation is requested

All heap allocation in the compiler and its runtime. This is a Project
Deviation covering `src/` and `include/` in full.

New code should call the `xalloc.h` wrappers rather than `<stdlib.h>` directly.
This is a project convention, not a MISRA requirement, and it is not currently
enforced by a tool.

## Consequences of non-compliance

Allocation failure aborts the process with a diagnostic rather than corrupting
state. Heap fragmentation is not a concern for a process that exits after one
compilation.

The residual risks are leaks and use-after-free, and these are real. ADR 0002
names reference cycles as the cost of the chosen memory model, with no cheap
fix. The compiler's own memory model documentation lists five further classes
that ARC does not reclaim, including multi-assign targets and unbound
temporaries.

Additional verification required by this deviation, all of which already runs:

- `arena-valgrind-probe`, `ast-free-leak-probe` and the other valgrind gates in
  `make verify-core`
- `far-transport-asan` (AddressSanitizer)
- `bin/fuzz_parse`, which found the 188-byte-per-assignment AST leak on
  2026-08-08

## Actions to control reporting

Rule 21.3 is suppressed project-wide in the cppcheck configuration rather than
per site, because a per-site suppression on 2,597 lines would be noise. The
suppression must name this record:

    --suppress=misra-c2012-21.3   # deviation D-01

Removing the suppression is the correct way to re-open this decision. Any
future move to a bounded allocator should start by deleting that line and
reading the report.
