> Rule 14.4: The controlling expression of an `if` statement and the
> controlling expression of an iteration-statement shall have essentially
> Boolean type.

## Summary

`if (ptr)` and `if (!ptr)` are the house idiom for a null check, and
`if (count)` for a non-zero check. Rule 14.4 requires `if (ptr != NULL)` and
`if (count != 0U)` instead.

Baseline: 2,111 reports in hand-written code.

## Detailed description

MISRA's rationale is that C's implicit conversion to a truth value hides the
comparison, and that a reader can misread `if (x)` when `x` is a value rather
than a flag. The rule exists to make the comparison explicit at every branch.

The concern is real but weak in this codebase, for two reasons. The dominant
shape by far is the null-pointer guard immediately after an allocation or a
lookup:

```c
PerformanceMonitor* monitor = xcalloc(1, sizeof(PerformanceMonitor));
if (!monitor) return NULL;
```

There is no ambiguity about what is being tested. The second reason is that C23
provides a real `bool`, and where this code has a genuine flag it uses it, so
the cases the rule is designed to catch — an integer masquerading as a
condition — are the minority.

## Justification

- **Comply, mechanically.** A rewrite of 2,111 conditions. It is achievable with
  clang-tidy, but it is a very large diff across the whole tree, it would
  conflict with every branch in flight, and it changes no behaviour. The value
  is readability, and the project's maintainers do not find the current form
  less readable.
- **Comply for integers only, keep the pointer idiom.** Attractive, and closer
  to where the risk actually is. Rejected only because cppcheck cannot express
  the split, so it would not be enforceable and would decay. Worth revisiting if
  the tooling improves.
- **Deviate.** Adopted.

## Conditions under which the deviation is requested

All controlling expressions of `if`, `while`, `for` and the conditional
operator throughout `src/` and `include/`.

## Consequences of non-compliance

The defect this rule guards against is a condition that tests the wrong thing —
most commonly `if (strcmp(a, b))`, which reads as "if equal" and means "if
different". That specific hazard is real and is **not** covered by this
deviation being in place, because no tool is now watching for it.

The mitigation is that cppcheck's own `knownConditionTrueFalse` check remains
enabled and fires on conditions that are provably constant, which catches the
subset where the mistake has a detectable consequence. The rest rests on review.
