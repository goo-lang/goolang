> Rule 17.2: Functions shall not call themselves, either directly or
> indirectly.

## Summary

The language being compiled has a recursive grammar and a recursive type
system. Expressions nest, types contain types, and blocks contain blocks. Every
pass over those structures is naturally recursive, and the parser is recursive
descent. Rule 17.2 forbids the shape of the whole front end.

Baseline: 805 reports in hand-written code.

## Detailed description

MISRA's rationale for Rule 17.2 is stack exhaustion. A recursive function's
stack use is bounded only by its recursion depth, and in an embedded system with
a small fixed stack and no overflow detection, an unbounded depth is an
unbounded fault. That reasoning is sound and its conclusion — ban recursion — is
the right call for the systems MISRA addresses.

It is the wrong call here for two reasons. First, the recursion depth is a
function of how deeply the *user's source file* nests, not of run-time data the
compiler cannot see. Second, this is a hosted process on an operating system
with a guard page: stack exhaustion produces a segmentation fault at a known
point, not silent corruption of adjacent memory.

The recursion is not incidental. `type_check_expression` recurses through
sub-expressions. `ast_node_free` walks the tree and its `->next` chains.
The escape analysis, the printer and codegen all do the same. Rewriting them
iteratively means hand-rolling an explicit stack in each pass, which moves the
same unbounded growth from the call stack to the heap while making every pass
harder to read.

## Justification

- **Explicit worklist in place of recursion.** The standard transformation. It
  is achievable for every pass, and it is what a truly deep-nesting-hardened
  compiler eventually does. It costs a rewrite of the type checker, the escape
  analysis, codegen and the printer, and it makes each of them substantially
  harder to follow. The benefit is a bound the process does not currently
  need. Rejected for now; reconsider if a real input is ever found that
  overflows the stack.
- **A depth counter with a hard limit.** Cheap, and it converts a crash into a
  diagnostic. This is the mitigation actually worth taking, and it is recorded
  as an action below rather than as a reason to comply.
- **Raise the stack limit.** Not a fix. It moves the cliff without removing it.

## Conditions under which the deviation is requested

Direct and indirect recursion in the compiler front end, middle end and back
end: parsing, type checking, escape analysis, code generation, AST traversal
and AST destruction.

It does **not** cover recursion in the emitted runtime that a compiled Goo
program links against. A runtime function that recurses on data supplied at run
time is a different risk and is not covered here.

## Consequences of non-compliance

A sufficiently deeply nested input program can exhaust the stack and crash the
compiler. On this platform the result is a segmentation fault, which is loud,
reproducible and not a memory-safety hazard.

The honest state of this risk: the depth is currently unbounded, and no probe
establishes the maximum nesting the compiler survives. That is a gap, not a
mitigated risk.

Actions arising, neither of which is complete:

1. Add a nesting-depth limit to the parser with a proper diagnostic, in the
   manner of the "expression nesting too deep" error that established compilers
   emit.
2. Add a probe to `make verify-core` that compiles a generated deeply-nested
   input and asserts a clean diagnostic rather than a crash.

Until those exist, this deviation accepts a crash on pathological input.
