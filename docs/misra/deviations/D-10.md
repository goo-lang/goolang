> Rule 21.4: The standard header file `<setjmp.h>` shall not be used.

## Summary

`goo test` implements `t.Fatal`, `t.Fatalf` and `t.FailNow`, which must stop the
current test and continue with the next one. The runtime does that with
`setjmp`/`longjmp` in `src/runtime/testing.c`.

Baseline: 3 reports in hand-written code.

## Detailed description

MISRA's rationale is that `longjmp` transfers control in a way that bypasses the
normal call and return discipline: automatic objects in the abandoned frames are
not destroyed in any orderly way, an object modified between `setjmp` and
`longjmp` has indeterminate value unless it is `volatile`-qualified, and calling
`longjmp` after the function that called `setjmp` has returned is undefined.

The use here is the narrow, well-understood one. `testing.Run` calls `setjmp`
before invoking a test function, and `t.Fatal` calls `longjmp` back to it. The
jump target's frame is guaranteed live because it is the direct caller. This is
the same mechanism Go's own testing package achieves with `runtime.Goexit`, and
the reason it is needed is recorded in the project's `goo test` documentation:
each test is passed to `testing.Run` as a value, which is what lets the runtime
own the call frame and `longjmp` out of `t.Fatal`.

## Justification

- **Return an error status from every test helper.** This is how a C test
  framework would normally do it, and it is wrong here, because the semantics
  being implemented are Go's. `t.Fatal` must stop the test at the point of call
  without the test author writing a `return`. A status return cannot express
  that.
- **Threads, with the test on its own thread that can be stopped.** A thread per
  test to avoid one `longjmp` is a large cost for a small mechanism, and it
  introduces the concurrency hazards `longjmp` does not have.
- **Deviate.** Adopted.

## Conditions under which the deviation is requested

`setjmp` and `longjmp` in `src/runtime/testing.c`, for the single purpose of
implementing the `t.Fatal` family's stop-this-test semantics, where the
`longjmp` target is the direct caller of the test function.

Any other use of `<setjmp.h>` is **excluded** from this deviation, including
using it for error propagation in the compiler itself.

**Two other headers include `<setjmp.h>`** and are not covered here:

| Header | Linked into `bin/goo`? |
|---|---|
| `include/transparent_execution.h` | no |
| `include/structured_concurrency_enhanced.h` | no |

Both belong to the Task #22-era framework code that P5.6 unlinked, so neither
reaches the shipped compiler. They are outside this deviation. Either bring
them under a record of their own with their own justification, or drop the
include along with the rest of that framework.

## Consequences of non-compliance

The two undefined behaviours to guard against are a `longjmp` to a returned
frame, and a non-`volatile` automatic object modified between the `setjmp` and
the `longjmp` being read afterwards.

The first cannot occur in the shape used: `testing.Run` calls `setjmp` and then
the test, and does not return until the test does or jumps back.

The second is the real residual risk, and it is worth a specific check. Any
local in `testing.Run` that is written after `setjmp` and read after the
`longjmp` returns must be declared `volatile`. That this holds has not been
verified against the current source, and it is the one concrete action arising
from this record.

Enforcement in place: `goo-test-probe` (`scripts/goo_test_probe.sh`) exercises
both a passing package and a failing one in `make verify-core`, so a broken
jump shows as a wrong verdict rather than silently.

## Actions to control reporting

Because there are only three sites, this is suppressed **inline** rather than
project-wide, so that a fourth site anywhere else in the tree is reported:

Outstanding action: audit the locals in `testing.Run` for the `volatile`
