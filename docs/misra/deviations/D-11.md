> Dir 4.12: Dynamic memory allocation shall not be used.

## Summary

Dir 4.12 is the directive form of the decision recorded in **D-01**. Rule 21.3
bans the `<stdlib.h>` allocation functions; Dir 4.12 bans dynamic allocation
however it is obtained. This record exists because satisfying D-01 by moving to
a non-`<stdlib.h>` allocator would not satisfy the directive, and the project
should not be able to claim it had.

Baseline: not measurable. No static analysis tool checks any MISRA directive
(MISRA section 6.5 explains why: given only the source, no algorithm can
guarantee to check a directive).

## Detailed description

The directive covers every source of dynamically allocated storage: the standard
allocators, a third-party allocator, a project-supplied pool, and the allocation
performed inside library functions the code calls. It is broader than Rule 21.3
in three ways that matter here:

1. **The arena allocator is in scope.** `arena { ... }` regions allocate
   dynamically even though they free in bulk.
2. **Allocation inside called libraries is in scope.** LLVM, curl and json-c all
   allocate on the project's behalf.
3. **The compiled program's runtime is in scope.** The Goo runtime that user
   programs link against allocates, and ARC is the mechanism that reclaims it.

MISRA's rationale is that dynamic allocation introduces failure modes that are
absent from static allocation: exhaustion, fragmentation, non-deterministic
timing, and the whole family of lifetime defects — use after free, double free,
and leaks.

## Justification

The reasoning in D-01 applies in full and is not repeated. The additional point
specific to the directive is that the project has chosen dynamic allocation
deliberately and has documented the choice, rather than arriving at it by
default:

- `docs/adr/0002-memory-model-arc-with-escape-analysis-elision.md` accepts
  automatic reference counting with escape analysis as the elision pass, and
  names reference cycles as the accepted cost.
- `docs/adr/0004-alias-based-escape-formulation.md` and
  `docs/adr/0005-escape-reasons-replace-the-escape-boolean.md` record how the
  elision decision is made and measured.

The alternatives considered are those in D-01. One further alternative applies
only at the directive level:

- **A whole-program static allocation budget for the compiled program's
  runtime.** This is what a MISRA-targeting language would do, and it is a
  legitimate future direction for a Goo profile aimed at embedded targets. It is
  not achievable for the general-purpose language as specified, because slices,
  maps and strings grow at run time.

## Conditions under which the deviation is requested

All dynamic allocation, in the compiler, in the runtime archive, and in the
libraries the compiler links against.

## Consequences of non-compliance

This deviation accepts the lifetime-defect family. The project's own record of
what is *not* reclaimed is the honest statement of the residual risk, and it is
maintained in `CLAUDE.md` and ADR 0002:

- reference cycles leak, with no cheap fix
- a local with a method set is unreleasable (the `CALLEE_VALUE` ceiling)
- a call to a callee the analysis cannot see marks its arguments as escaping,
  which is `CALL_OPAQUE`, the largest reason in the corpus at 578 locals
- a multi-assign target gets no store release
- an unbound temporary has no release site at all

Verification in place, all of it running today:

| Instrument | What it covers |
|---|---|
| `arena-valgrind-probe` | use-after-free and double-free in arena regions |
| `ast-free-leak-probe`, `ast-free-census` | the `ast_node_free` leak class |
| `arc-release-probe` and the ARC probe family | that release sites are emitted where the analysis says they are |
| `far-transport-asan` | AddressSanitizer on the transport layer |
| `bin/fuzz_parse` | parser-driven allocation paths |
| valgrind on `bench/daemon/daemon.goo` | 0 errors at 400,000 requests |

## Actions to control reporting

No tool reports this directive, so there is nothing to suppress. The control is
this record plus the probe net above.

Re-open this decision if a Goo profile for embedded targets is ever specified.
That profile, not the general-purpose language, is where Dir 4.12 becomes
achievable.
